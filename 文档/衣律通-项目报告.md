## 二、为什么选这个题

一件 200 元的衣服货不对板，维权的经济账是负的：律师咨询费按小时计，可能超过商品本身；自己写起诉状，格式、事实组织、法条引用三关都过不去；向平台投诉，往往被"建议先与商家协商"踢回来。

这个断层里缺的不是信息，是**转化能力**——知道该维权，但不知道怎么写、怎么写才有效。

法律文书的门槛很具体，就三件事：

1. **格式对不对**：当事人信息、诉讼请求、事实与理由、证据清单，缺一不可
2. **事实怎么组织**：把"衣服色差很大"转成"商品实际交付物与详情页描述在面料成分、颜色色号上存在实质性不符"
3. **法条引哪一条**：《民法典》577 条还是 582 条，《消保法》24 条还是 55 条，差一条不成立

这三件事都可以被结构化解构。我做的就是把它们拆成表单字段，再用 AI 补上"翻译"这一层。

## 三、技术架构

```
表现层  WXML / WXSS（17 页 + 深色模式 CSS 变量主题）
   ↓
逻辑层  BaseFormPage（789 行模板方法基类）
        BaseDetailPage / scrollBehavior
   ↓
服务层  ArticleService / DocumentService / UserService（单例）
   ↓
工具层  aiService · documentUtils · pdfUtils · privacyUtils · errorHandler
   ↓
数据层  云数据库（article / documents / user / comments）
        云函数（contentCheck / encryptData / generateDocumentPDF / searchCourts）
        云存储（banner / 文章图 / PDF）
```

设计上的取舍：**没有引入任何框架**（Taro / uni-app 都没用）。原因是项目只需要跑在微信一端，框架带来的构建链路和多端抽象在这个场景里是纯成本。换来的代价是页面间的复用必须自己解决——这也是基类存在的原因。

## 四、三个核心技术实现

### 4.1 模板方法基类：消掉三份近似代码

三种文书（民事起诉状、举报信、协商函）的流程骨架几乎一致：五步向导 → 逐步校验 → 草稿自动保存 → 免责声明 → 生成预览 → 导出 PDF。

如果各写一遍，是 3 × 800 行的高度重复代码。维护时的典型场景是：改一处 PDF 导出逻辑，要同步改三个文件，漏一个就是线上不一致。

`utils/baseFormPage.js` 抽出公共骨架，用三种手段控制差异：

**抽象方法**（子类必须实现，基类 `throw new Error` 强制契约）：

```js
getDocumentType()      // 'civil_complaint' | 'report_letter' | 'negotiation_letter'
generateDocumentTitle() // 标题格式各异
validateStep(step)      // 各步校验规则不同
```

**钩子方法**（有默认实现，子类按需覆写）：

```js
onDraftLoaded(draft) {}   // 草稿载入后
onStepChange(from, to) {} // 步骤切换时
getExtraDraftData()       // 附加到草稿的额外字段
```

**模板方法**（基类定义流程，不暴露细节）：`nextStep()` 内部固定按"校验 → 存草稿 → 切步骤 → 触发钩子"顺序执行，子类无法打乱。

效果：三个表单页合计约 2,300 行（`complaint-form` 1,370 / `negotiation-form` 565 / `report-form` 398），差异全部收敛到覆写方法。派生的详情页更极端——`report-detail.js` 67 行，`negotiation-detail.js` 29 行。

**踩过的坑**：初版子类覆写了 `onLoad` / `onShow` / `nextStep`，导致基类的隐私初始化、草稿恢复被跳过。后来改为子类只调用 `BaseFormPage.onLoad.call(this, options)` 并改用 `onDraftLoaded` 钩子。这类问题的根因是继承层次里"覆写"和"扩展"的边界没划清。

### 4.2 AI 文书生成：约束 + 清洗双保险

这是产品的核心，也是最容易做砸的地方。

**问题**：直接把用户填的内容拼成 prompt 丢给大模型，输出会带上标题（"事实与理由"）、落款（"此致 / 具状人 / 年月日"）、Markdown 标记，以及"综上所述，恳请贵院依法支持原告全部诉讼请求"这类套话。这些系统都会自动加，模型再加一遍就重复了，格式直接崩。

**第一层：约束 Prompt**（`utils/aiService.js`）

六条硬规则写进 system 部分：

```
1. 【禁止标题】不输出"事实与理由""一、事实部分"等任何标题
2. 【禁止落款】不输出"此致""具状人""年月日"
3. 【禁止Markdown】不使用 **加粗**、# 标题，仅输出纯文本
4. 【禁止重复结尾】不输出"故原告特向贵院提起诉讼…"
5. 【内容要求】重点描述侵权/违约事实 + 引用具体法条
6. 【强制分段】按"交易背景""侵权事实""法律依据"分段
```

**第二层：后处理清洗**（模型不会 100% 听话）

```js
cleanAIText(text) {
  // 1. 剥 Markdown
  // 2. 去掉可能跑出来的标题行
  // 3. 在"此致/具状人/综上所述"处截断落款
  // 4. 移除模型自造的"故原告…"（系统统一拼接）
}
```

这里有个细节值得记：早期版本用 `/故原告.*$/` 粗暴截断，结果把"故原告认为…"这种正常论述也切了。后来把正则收窄到只匹配结尾请求语。

**第三层：流式输出**

```js
const model = wx.cloud.extend.AI.createModel("hunyuan-exp");
const res = await model.streamText({
  data: { model: "hunyuan-turbos-latest", messages: [{ role: "user", content: prompt }] }
});
for await (let chunk of res.textStream) onProgress(fullText += chunk);
```

用户能看到文字逐段出现，不用干等。同时做了并发限制的错误分类处理（`EXCEED_CONCURRENT_REQUEST_LIMIT` 单独提示"AI 服务繁忙，请稍后重试"）。

### 4.3 法院推荐：从"能返回"到"返回对的"

用户通常不知道该去哪个法院起诉。`cloudfunctions/searchCourts` 走腾讯地图 POI 检索，关键词"人民法院"，限定 `category:130502`。

**第一版的问题**：POI 数据里混着大量非法院机构——法院旧址、法院家属院、法院宿舍楼、法院对面的打印店。用户看到一屏"XX区人民法院旧址"。

**解法三层**：

1. **45 个关键词黑名单**（旧址、宿舍、家属、住宅、公寓、食堂、停车场、打印、复印、超市、便利店、公交、车站…）
2. **名称长度升序排列**：本级法院名称通常最短，"重庆市南岸区人民法院"排在"重庆市南岸区人民法院诉调对接中心"前面
3. **多级兜底**：API 无结果或失败时，按省市区拼出标准的"XX市XX区人民法院"

这三点做完，功能才真正可用。

### 4.4 顺带一提：PDF 中文字体

云函数里用 `pdfkit` 生成 A4 文书，最大的坑是中文字体。`pdfkit` 内置字体不含中文，不加载字体文件的话整篇是方框。

处理方式：把 `normal.ttf` 打包进云函数目录，生成时 `doc.font(路径)` 显式加载。

还遇到过另一个问题：用户在 `editor` 组件里编辑后，半角数字和点号可能被输入法转成全角，而字体文件不含全角字形，PDF 里诉讼请求的序号就变成方框。定位方法是逐字符比对 Unicode 范围（半角 `U+0030-0039` vs 全角 `U+FF10-FF19`）。

## 五、一次真实的挫折：提审被驳回

这是整个项目里最有价值的一段经历。

### 5.1 发生了什么

小程序提审，被驳回。理由是：

> 小程序涉及收集、存储用户身份信息，平台暂不支持此功能

截图指向**民事起诉状生成页面**——用户需要填姓名、身份证号、手机号、地址。

### 5.2 为什么

去查了平台规范和个保法，结论是：

- 身份证号属于《个人信息保护法》明确的**敏感个人信息**，收集需要单独、明示、自愿的同意，且需具备特定充分目的
- 《微信小程序平台运营规范》15.1.3：除非法律要求或经用户同意，否则不得要求用户输入个人信息才可使用功能
- 《常见类型移动互联网应用程序必要个人信息范围规定》列出的可收集身份证号的小程序类型只有金融、交通票务、寄递、二手车、问诊等，**法律服务类不在其中**
- 微信未开放直接获取身份证号的 API，只能通过表单让用户主动填写；核验必须走官方的城市服务实名校验接口，禁用第三方

也就是说：**我不能把身份证号做成必填**。

### 5.3 怎么改

四件事，核心思路是把采集边界缩到最小：

| 改动 | 实现 |
|---|---|
| 身份证号改为**可选** | 不填也能生成文书，法院立案时可补录 |
| 收集前**单独弹窗告知** | 说明用途、范围、存储方式、用户权利，不默认勾选 |
| **脱敏展示** | `maskIdCard()` 只显示首位和末位，其余打码 |
| **加密存储** | `encryptData` 云函数处理敏感字段后再落库 |

这些能力抽成 `utils/privacyUtils.js`（210 行）公共模块，三个表单页共用：

```js
maskIdCard(idCard)          // 首末位保留，中间打码
encryptObjectFields(obj)    // 指定字段加密
needsIdCardConsent(type)    // 按文书类型判断是否需要同意弹窗
savePrivacyConsent(...)     // 同意记录持久化
```

### 5.4 这段经历的收获

合规不是"加个弹窗"就完事。真正要回答的是：**这个字段是不是非收不可？** 我原来的设计里身份证号是必填的，因为"起诉状本来就要写"。但拆开看：起诉状需要身份证号是为了法院立案核对当事人身份，而生成文书这一步并不需要。把它拆成"生成时可空、立案时补录"，问题就解了。

这也是我第一次认真读《个人信息保护法》和平台运营规范，而不是凭感觉做产品。

## 六、代码质量与自我审查

开发过程中用 AI 辅助做了三轮代码审查，留下了完整记录（`文档/code_review_report*.md`、`fix_verification_report.md`）。

审查发现的真实问题，举两个：

**问题 1：链式 `.where()` 不会累加条件**

```js
// 错误写法
let q = db.collection('documents').where({ _openid: '{openid}' });
if (type) q = q.where({ type });   // ❌ 覆盖了前一个条件
if (status) q = q.where({ status });
```

微信云数据库的链式 `where` 是**覆盖**而非追加。这意味着同时传 `type` 和 `status` 时，`_openid` 隔离条件丢失，可能返回其他用户的数据。

修复：构建完整条件对象后一次性 `.where()`。这个 bug 如果没被查出来，是一个真实的数据越权漏洞。

**问题 2：缓存与脏读**

`UserService` 加了 5 分钟 TTL 缓存减少 N+1 查询，但写操作后没失效缓存，导致更新昵称后页面仍显示旧值。修复是写操作传入 `useCache: false` 并主动 `invalidateCache()`。

**我对这些 AI 审查结果的判断**：审查报告给的"A- / 88 分"这类评分我**不采信**，因为评分标准是模型自己定的，没有可比性。有价值的是具体的问题定位和修复方案，这些我能自己验证。

## 八、如果重做，我会改什么

1. **先建 git 仓库**。这个项目开发期间没有版本控制，靠文件修改时间回溯进度，导致现在无法展示提交历史。这是最该改的习惯。
2. **AI 输出加自动化测试**。现在是人工看生成结果对不对，应该把"是否含标题""是否含落款""是否引用了法条"做成断言，每次改 prompt 跑一遍。
3. **把提示词和清洗逻辑分开验证**。约束 Prompt 和后处理清洗是两道防线，但混在一起改的时候容易互相掩盖问题——prompt 改坏了，清洗逻辑兜住，反而看不出退化。
4. **上线前就跑合规检查**。提审被驳回浪费了一轮时间，其实只要提前读一遍平台运营规范就能避免。

## 九、为什么投 AI 部门

这个项目里 AI 不是装饰。混元模型承担了"生活语言 → 法律语言"的翻译，是整个产品成立的前提——没有它，用户填完表单拿到的还是模板填空，不是能用的文书。

并且我是从**工程约束**的角度在用模型，而不是调 API 就完事：六条 Prompt 约束、流式输出、后处理清洗、错误分类处理，这些都是为了让模型输出能真正进生产。

我长期想做的方向是 Agent 工具开发。这个项目给我的启发是：模型能力不是瓶颈，**如何把模型能力约束到可交付的状态**才是。这与做一个可靠的 Agent 工具是同一件事。
